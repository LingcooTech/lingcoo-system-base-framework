# 后台任务、Outbox 与通知

## 定位

这一层负责“稍后可靠执行”和“向账号传递系统消息”，不包含课程提醒、订单通知或内容发布等领域
规则。领域模块只负责在自己的事务中写入 Outbox 事件，或用稳定幂等键创建任务与通知。

## 持久化任务

`job_runs` 保存队列、任务类型、JSON 载荷、幂等键、优先级、最大尝试次数和执行状态。Worker 使用
数据库行锁原子领取单个任务；失败后按指数退避重新调度，耗尽尝试次数后进入 `dead`，管理员可在
任务中心重新入队。Worker 崩溃遗留的运行锁会按超时自动恢复。

任务处理器通过 `JobHandlerRegistry` 显式注册，禁止根据载荷动态加载代码。任务列表 API 不返回
`payload` 和 `result`，避免领域数据或外部服务信息从运维界面泄露。任务载荷仍应只保存执行所需的
标识符，不应保存密码、令牌或 Provider 凭据。

## 事务 Outbox

需要“业务状态已提交后事件不能丢”的模块，应在同一个数据库事务中写入 `outbox_events`。独立
Worker 领取并分发事件，成功后标为 `published`；失败采用同样的退避和死亡机制。订阅器可能因为
进程在执行完成与确认之间退出而被重复调用，因此必须使用事件 ID 或领域幂等键防止重复副作用。

密码修改已作为框架示例：密码、会话撤销和 `auth.password_changed` 事件在同一个事务中提交；通知
策略随后生成安全提醒。

## 通知与邮件投递

`notifications` 是站内通知事实，按账号维护 `unread`、`read` 和 `archived` 状态。管理员可发布
全员公告；每个接收账号都使用独立幂等键。站内通知不依赖任何外部服务。

启用邮件时，`notification_deliveries` 记录目标、SMTP 连接、任务和最终状态；实际发送由
`notification.email.deliver` 任务调用已启用的 SMTP Provider。发送失败会保留安全化错误信息，
并进入任务重试流程。没有可用 SMTP 时，要求邮件投递的公告会被拒绝，纯站内通知不受影响。

## 领域接入约束

1. 使用稳定、可复现的幂等键，避免重复任务和重复通知。
2. 业务事务需要可靠事件时直接写入 Outbox，不要在提交后再发内存事件。
3. Handler 必须可安全重复执行，并设置合理超时；外部调用优先使用 Provider 层。
4. 通知正文只用于用户沟通，不承载业务状态；真实状态仍从对应领域读取。
5. 新任务类型必须显式注册、具备失败语义和测试，并能在不配置外部服务时保持系统可启动。

## 运行与健康

本地使用 `npm run dev:worker`。生产环境的 `worker` 与 `api` 使用同一镜像，分别运行
`dist/worker.js` 和 `dist/server.js`。Worker 在 `WORKER_HEALTH_PORT` 提供内部健康探针；部署只有在
迁移成功、Worker 健康且公开 `/ready` 通过后才完成。
